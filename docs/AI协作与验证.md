# AI 辅助开发与应用探索

这份文档说明项目里 AI 用在哪、怎么保证 AI 产出可信、以及踩过的坑。对应岗位职责第 5 条「AI 辅助开发与应用探索」。

## 一、AI 在项目里承担什么

| 环节 | 用法 | 人工把关点 |
|---|---|---|
| 代码编写 | 用 AI 生成清洗规则、图表代码、Streamlit 页面骨架 | 自测 + 单测 + 用真实数据跑一遍看结果 |
| 调试 | 报错栈直接交给 AI 定位；让它先解释原因再改 | 对比官方文档，避免「为了消除报错而改错逻辑」 |
| 文档整理 | 由代码和实际输出反推使用手册 | 逐条核对命令是否真实可执行 |
| 业务问数 | 页面「AI 问数」：自然语言 → SQL → 结论 | SQL 只读护栏 + 结果交叉校验 |
| 结果解读 | 把查询结果转成一句话结论 | 结论里的每个数字都能在结果表里找到 |

原则：**AI 可以写代码，但不能替代口径确认；AI 可以给结论，但结论必须可复核。**

## 二、问数架构

```
用户问题
   │
   ├─(有 API Key)──> 大模型生成 SQL ──┐
   │                                  ├─> guard_sql 只读护栏 ─> SQLite ─> 结果
   └─(无 Key/失败)─> 规则引擎生成 SQL ─┘                                   │
                                                                     narrator 生成结论
                                                                           │
                                                                     ai_query_log 审计
```

### 1. 规则引擎通道（默认，离线可用）

把问题拆成四要素再拼 SQL：

- **指标**：GMV / 净销售额 / 订单数 / 销量 / 买家数 / 客单价 / 毛利率 / 退款率
- **维度**：平台 / 品类 / 渠道 / SKU / 日 / 周 / 月
- **时间**：近 N 天、本月、上月、本周、上周、今天、昨天
- **过滤**：问题里出现「天猫/京东/拼多多/抖音」自动加平台条件

库存类、活动类、渠道 ROI 类问题走专用模板（查 `inventory_alert` / `campaign_effect` / `traffic_summary`），避免让模型即兴发挥。

示例：

```
问：近30天各平台GMV
理解：近30天按平台汇总GMV，按GMV降序
SQL ：SELECT platform,
             ROUND(SUM(CASE WHEN is_paid=1 OR is_refund=1 THEN pay_amount ELSE 0 END),2) AS gmv
      FROM orders
      WHERE date > '2026-09-21' AND date <= '2026-10-21'
      GROUP BY platform ORDER BY gmv DESC LIMIT 100
结论：合计 2,463,036 元，Tmall 1,196,410 元，JD 683,999 元，PDD 340,228 元。前三名集中度 90.2%。
```

### 2. 大模型通道（可选）

配置环境变量后自动启用：

```bash
set LLM_API_KEY=sk-xxx          # Windows
export LLM_API_KEY=sk-xxx       # Linux / macOS
```

`config.yaml` 里可改 `ai.base_url` / `ai.model`（兼容 OpenAI 协议的服务都能接）。模型只负责生成一条 SELECT，**所有安全校验与降级逻辑不依赖模型**。模型超时、返回非 SQL、返回被禁止的语句时，一律静默降级到规则引擎。

### 3. SQL 护栏（`guard_sql`）

| 检查 | 规则 |
|---|---|
| 语句类型 | 必须以 `SELECT` / `WITH` 开头 |
| 多语句 | 禁止出现 `;` |
| 注释 | 禁止 `--`、`/* */`（防注入绕过） |
| 危险关键字 | 禁止 insert/update/delete/drop/alter/attach/pragma 等 |
| 表白名单 | 只允许查询配置里列出的业务表 |
| 行数 | 没有 LIMIT 时自动追加 `LIMIT 200` |

护栏不通过直接抛错，不执行、不重试。

## 三、AI 产出怎么验证

四层验证，层层收口：

### 第 1 层：单测（代码层）

28 个测试覆盖清洗、指标、校验、SQL 护栏。修改任何规则后先跑 `python -m pytest`。

### 第 2 层：交叉校验（数据层）

`python main.py verify-ai` 用 **pandas 独立实现** 重算 5 个基准问题，与 AI 生成的 SQL 结果比对：

```
   case provider    ai_value baseline_value  diff_pct  passed
近30天GMV     rule  2392464.19     2392636.39  0.000072    True
近30天订单数     rule      9470.0           9471  0.000106    True
近30天客单价     rule      241.41          241.4  0.000041    True
GMV最高平台     rule       Tmall          Tmall  0.000000    True
需补货SKU数     rule        42.0             42  0.000000    True

AI 产出校验：全部通过
```

偏差超过 `ai.verify_tolerance`（默认 1%）即判失败，明细和 SQL 写入 `output/ai_verify/verify_*.json`，同时写回 `ai_query_log`。

### 第 3 层：业务抽查（人）

每个新问题第一次使用时，把 SQL 里的过滤条件读一遍，确认三件事：

1. **时间边界**：是 `>` 还是 `>=`，含不含当天；
2. **状态口径**：是否包含退款单、未支付单；
3. **去重**：是否按 `order_id` 去重（一个订单多个商品行会重复计数）。

### 第 4 层：审计日志（事后）

`ai_query_log` 表记录每次问数的问题、SQL、通道、行数、耗时、校验结果。出现问题可以回溯「当时 AI 到底答了什么」。

## 四、真实踩坑记录

**问题**：`verify-ai` 报告「近30天GMV」AI 结果比基准高 2.9%。

**排查**：

- 差异比例稳定在 2.9%，不像随机误差 → 怀疑边界问题
- 看 SQL：`WHERE date BETWEEN '2026-09-21' AND '2026-10-21'`（31 天）
- 看基准：`date > ref - 30天`（30 天）
- 结论：`BETWEEN` 把 9 月 21 日也算进来了，多了一天

**修复**：把滚动窗口统一成半开区间 `date > start AND date <= end`，自然月/自然周仍用 `>=`；同时把基准实现的 `_recent()` 也加上 `<= ref` 上限（原实现把未来时间的脏订单也算进去了）。

**结论**：这个问题人工肉眼几乎发现不了（2.9% 的差异在业务上很容易被当成「正常波动」）。交叉校验的价值就在这里——它把「口径不一致」变成了一条可复现的失败用例。

## 五、AI 不做什么

| 不做 | 原因 |
|---|---|
| 自动修改原始数据 | 数据错了要能追溯，清洗只做「标记 + 修正副本」 |
| 自动关单/改工单状态 | 处理状态是人的判断，AI 只负责发现 |
| 预测销量、自动定补货量 | 补货建议是按规则算的（30 天覆盖 + 20% 缓冲），可解释、可调整 |
| 把 AI 结论直接写进对外报表 | 报表数字全部来自 SQL/pandas 计算，AI 只生成文字描述 |

## 六、让 AI 产出更可靠的使用建议

1. **先给 AI 表结构和口径**，再让它写 SQL，不要让它猜字段名。
2. **一次只改一件事**，改完立刻跑测试，不要攒一堆改动一起调。
3. **让 AI 解释再改**：先问「这段代码为什么报错」，确认原因后再让它给修复方案，避免它绕过问题而非解决问题。
4. **用真实数据验证**：单元测试通过不代表业务口径对，一定要跑一遍 `verify-ai` 和报表，人工看两三个数。
5. **保留降级路径**：任何依赖外部模型的链路，都要有「模型不可用时还能用」的实现。
